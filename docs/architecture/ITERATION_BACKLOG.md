# 架构迭代机制与待办清单

> 本文回答「如何持续优化迭代」：把迭代变成**有目标、有证据、有记录、有完成定义**的固定动作，而不是随机地扩写文档或堆功能。
> 关联：总纲 [`docs/ARCHITECTURE.md`](../ARCHITECTURE.md)（v2.1，尤其 §17–§18）、变更记录 [`CHANGELOG.md`](../../CHANGELOG.md)。

---

## 1. 迭代原则

1. **立场稳定，实现可变**：§1 的质量属性排序，以及 ADR-01（闭环优先）、ADR-02（树模型主力）、ADR-03（私有化优先）、ADR-12（MVP 范围）属于架构立场，变更必须走评审并新增 ADR 说明取舍；其余实现细节可迭代。
2. **先证据，后实现**：任何涉及推荐策略或模型效果的改动，先用 §17 的手段产出证据（尤其 §17.2 离线回放），再写代码。避免「先搭平台、最后发现策略无效」。
3. **文档先行、同批提交**：架构变更先更新 ADR 与 `ARCHITECTURE.md`，再改实现，且文档与代码在同一次提交中落地；不允许代码先行、文档后补。
4. **每轮只解一个主矛盾**：一轮围绕一个可验证目标，其余进 backlog 排队。这是 ADR-12 在迭代节奏上的延伸。
5. **数据红线不可协商**：任何迭代都不得把真实配方、实测数据、模型权重、密钥带入仓库、测试 fixture 或演示环境；自动化测试只用合成或脱敏数据（§17.3）。

---

## 2. 每轮迭代的固定动作与完成定义（DoD）

| 步骤 | 必须产出 | 判定标准 |
|---|---|---|
| 1 明确目标 | 一句话目标 + 对应 backlog 编号 | 目标可被一个指标或一条检查单验证 |
| 2 记录决策 | 新增/修订的 ADR 条目 | 含备选方案与取舍理由 |
| 3 实现 | 代码 / 文档变更 | 依赖方向符合 §18.1 |
| 4 验证证据 | 测试、回放报告或检查结果 | 命中 §17 对应层的门禁 |
| 5 文档同步 | `ARCHITECTURE.md`、本文、`CHANGELOG.md` | 三处一致，无过时描述 |
| 6 上线检查 | §17.5 go/no-go 检查单（涉及发布时） | 全项通过或有书面例外 |
| 7 复盘 | 迭代记录表 + 下轮目标 | 遗留问题进入 backlog |

> **缺少第 4 步或第 5 步的迭代不算完成。** 这条约束专门用来防止「文档很丰满、系统没验证」的伪迭代。

## 3. 优先级定义

| 级别 | 含义 | 排期规则 |
|---|---|---|
| P0 | 阻塞立项验证或承载最大风险，不做则后续工作可能白费 | 下一轮优先，且优先于功能开发 |
| P1 | 直接支撑 MVP 交付 | 一期范围内排入 |
| P2 | 提升可信度 / 交付体验 / 对外表达 | 二期或穿插进行 |
| P3 | 探索性、依赖外部条件 | 条件满足后再评估 |

## 6. 下一轮（R2）建议

**单一主矛盾**：把「纸面领域模型」变成「可运行、且能证明有效」的最小系统。

三项交付物：

1. `db/migrations/001_init_schema.sql` —— 落实 B01，含枚举、约束、索引、RLS 策略与扩展-收缩兼容设计。
2. `tests/replay/` —— 落实 B02，产出「推荐策略 vs 随机 / 历史顺序 / 单目标贪心」的轮次对比报告（合成数据或已脱敏历史序列）。
3. Walking skeleton —— 落实 B03，用合成数据跑通 §18.2 十步，重点验证「下一轮推荐确实发生变化」。

**验收**：DDL 可无错执行并回滚；回放报告能给出轮次下降分布及置信区间（而非单点数字）；walking skeleton 端到端可演示且审计可反查。

**R2 明确不做**：真实数据接入、多租户管理 UI、LIMS 对接、知识图谱、生成模型、GNN、私有 LLM。

> 幸存者偏差诊断已并入 B02 交付（附录 B.1 已定，依据见 §17.2）：先核查历史序列 `failed / cancelled` 占比，再选择全量回放或「合成数据 + 受控注入偏差」的保守回放；保守模式下报告必须显式标注幸存者偏差风险，不得直接对外引用轮次下降数字。
