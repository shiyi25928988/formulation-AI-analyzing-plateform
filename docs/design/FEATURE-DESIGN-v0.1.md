## 1. F1 预测-实测校准追踪

**问题**：客户凭什么相信预测区间？架构要求区间必经 conformal 校准并必返，但产品层没有任何地方展示「模型过去说得准不准」。信任建立是化工场景的核心卖点，这块能力目前是隐藏的。

**设计**：
- 新界面（导航挂「配方工作台」子页）：按指标维度的**校准曲线 + 区间覆盖率追踪**。X 轴为名义覆盖率（50/70/90%），Y 轴为实测覆盖率，理想为对角线；叠加按月的时间序列展示「最近 3 个月 vs 全历史」，覆盖率随数据积累收敛的过程可视化。
- 每条曲线标注样本数 n 与样本来源（均为真实实验回写，`test_result` × 历史 `prediction_log` 经 `lineage_edge` 关联）。
- 覆盖率偏离名义值时按分档给出**黄/红警示**与处置建议（触发重校准 / 检查分布漂移），联动 F4（阈值与分档见 F1 详设 §3.3：-5pp 关注 / -10pp 异常）。
- UI 组件复用原型 `MetricCard` 的区间条视觉语言，保持一致。

**架构依赖**：`prediction_log` / `test_result` / `lineage_edge` 表（§3.2）；conformal 校准服务；统计物化表 `calib_stat`（新增表，随 B01 DDL 一并评审）。
**验收标准**：能按指标查看名义 vs 实测覆盖率；样本 <30 时明确显示「样本不足，仅供参考」而非空图。
**边界（不做）**：不做在线 A/B；不做跨指标合成评分（每个指标独立看）。

## 2. F2 配方版本对比（Diff）

**问题**：架构 §7.3 承诺了血缘双向查询与配方版本管理（F-2026-0184 v3 这类版本号已在原型中出现），但「v2 和 v3 到底差在哪」没有产品承接。配方工程师改配比后最自然的动作就是对比。

**设计**：
- 配方工作台新增「对比版本」入口：选择任意两个版本 → 左右双栏组分表 + **差异高亮**（配比变化 / 组分增删 / 工艺参数变化）。
- 差异下方自动带出**两版预测结果对照**（含区间变化）与**实测结果对照**（若均已回写实验）。
- 每行差异可跳转血缘视图：「这个变化影响了哪些预测 / 被哪些实验采纳」。
- 导出对比报告（走审批流，带水印）。

**架构依赖**：`formula_version` / `formula_component` 不可变快照；`lineage_edge` 反向查询。
**验收标准**：任意两版本 diff 正确；对比结果含预测与实测两栏；血缘跳转可达。
**边界（不做）**：不做三方合并对比；不做自动归因「哪个差异导致性能变化」（组分共线，归因交给工作台分组归因 §5.2；F1 异常样本下钻可辅助定位）。

## 3. F3 离线批量筛选

**问题**：§3 数据流明确支持「离线批量预测（大批量虚拟配方筛选）」，原型只有单配方交互路径。客户常见场景是「我有 5000 个候选配比组合，帮我筛出达标的前 50 个」——这是最容易被销售提及、却还没有产品形态的能力。

**设计**：
- 新界面「批量筛选」：上传虚拟配方集（CSV 模板，走 `examples/` 脱敏模板口径）→ 创建异步任务（Celery）→ 进度条与分片状态 → 结果表（达标/不达标/拒答三类标记）→ 达标集一键转推荐（进实验管理看板）。
- 结果页沿用预测卡口径：每行数值带区间，OOD 按**两级处置**（架构 §4.3）——severe 行显式标「拒答」不给数，advisory 行返回数值并带 `advisory_only` 黄标——批量场景更容易静默失败，此口径不可放松。
- 任务级 provenance：任务记录模型/特征/快照三元组；**结果导出走 F5 审批流**（ExportRequested 双人审批），通过后文件带水印与版本码。
- 配额与限流（默认值可配，租户级）：单任务 ≤ 10,000 行、单租户并发 ≤ 2 个任务、5,000 行任务目标完成 ≤ 15 分钟（走离线通道，不占在线推理预算 §15.2）。
- 关键异常态（防静默失败延伸）：CSV 模板校验失败 → 整单拒绝并逐行标注错误；部分行解析失败 → **失败行不静默丢弃**，单独标记并可下载修正后重提；任务失败 → 保留分片中间产物，断点续算；配额耗尽 → 明确报错与排队提示。

**架构依赖**：Celery 任务队列、MinIO 结果文件、`ExportRequested` 事件幂等语义。
**验收标准**：5000 行任务全链路可跑通且进度可查；severe OOD 行不输出数值、advisory 行带黄标；任务记录含 provenance 三元组；结果导出强制走 F5 审批；部分行失败可下载修正。
**边界（不做）**：不做在线实时大批量（走离线通道）；一期不做筛选结果自动排序优化（按达标率排序即可）。

## 4. F4 数据质量看板

**问题**：数据红线（新数据强制全记录失败与取消、QC 规则、回写完整率）都是「平台自己保证」的承诺，但承诺需要**证据面**——给客户管理员和管理层看的健康度页面。这也是白皮书「可审计」卖点的产品落点。

**设计**：
- 新界面（可见角色：研发主管、只读审计员——聚合统计不豁免明细行密级，下钻仍走 ABAC）：四张看板——
  1. **QC 规则命中统计**：按规则编号统计近 30 天命中/阻断次数；阻断率较前 30 天基线升高 >10pp 或绝对值 >15% 时触发告警（阈值可配，默认值随部署固化），提示排查采集问题。
  2. **失败/取消记录占比**：历史库占比核查 + 新数据占比趋势（§17.2 幸存者偏差三步诊断的第一步，产品化）。
  3. **回写健康度**：待回写积压、平均回写延迟、超期分布（与实验管理看板联动，那里是操作视角，这里是管理视角）。
  4. **训练集构成**：实测/仿真/文献三档占比、密级分布、快照时间跨度。
- 所有数字可下钻到明细行，明细导出走审批。

**架构依赖**：`audit_event` / `qc_flag` / 数据红线规则库；快照元数据。
**验收标准**：四张看板均可下钻；失败记录占比口径与 §17.2 一致；历史库不完整时显示「存量不完整」标注而非误导性比例。
**边界（不做）**：不做自动清洗动作（只诊断、只报警，清洗是二期数据工具的事）。

## 5. F5 导出审批工作台

**问题**：§8.2 双人审批 + 水印在原型里只是一个「导出（审批中）」按钮，审批人侧完全没有界面。审批流是合规承诺，断在产品层等于没做。

**设计**：
- 审批人视角新界面：待办队列（导出请求：谁、导什么、密级、理由）→ 查看脱敏预览 → 双人会签（第二人不可为发起人）→ 通过后生成水印文件并记录审计事件。
- 发起人视角：申请状态追踪（待一审/待二审/已通过/已拒绝 + 拒绝理由）。
- 全程事件走 `ExportRequested` 幂等 + 审批状态机（§16.4 口径），防重复导出。
- 审批超时处置：待审超 48 小时自动升级提醒研发主管，超 5 个工作日转派备份审批人（规则可配），杜绝审批流卡死。

**架构依赖**：审批状态机、水印服务、`audit_event`。
**验收标准**：双人会签不可同人；拒绝必填理由；通过后文件水印与审计可追溯。
**边界（不做）**：一期不对接企业 OA 审批（二期 LIMS/ERP 集成时一并考虑）。

## 6. F6 通知与待办中心

**问题**：闭环靠状态机驱动，但状态流转目前靠用户自己刷页面。§16 已定义事件目录，产品层缺一个统一的「事件 → 人」出口，否则「推荐完没人回写」的老问题只是换了位置。

**设计**：
- 顶栏铃铛 + 待办中心页，事件源（一期只接三类）：
  1. **闭环超时**：实验超 7 天未回写（默认阈值，租户级可配）→ 提醒实验员，超期升级提醒研发主管；
  2. **审批待办**：导出审批到达（联动 F5）；
  3. **模型生命周期**：重训完成/灰度上线/金丝雀基准集回归失败（`CanaryFailed` 事件，§16.4）→ 提醒研发主管与系统管理员。
- 渠道为租户级开关（站内信默认开启；邮件可选走内网 SMTP，按人偏好配置）；不做 IM 推送（依赖客户 IM 集成，二期评估）。
- 通知可追溯：每条通知记录事件 ID，点击跳转对应对象（实验卡 / 审批单 / 模型版本）。

**架构依赖**：事件目录（§16.4）、Celery 定时任务、幂等投递。
**验收标准**：三类事件端到端可达；同一事件不重复提醒（幂等键）；跳转目标正确。
**边界（不做）**：不做自定义订阅规则引擎（固定三类即可，避免配置复杂度）。

## 9. 优先级与节奏建议

1. **P1（随 R2/R3 落地）**：F1 校准追踪、F2 版本对比、F4 数据质量看板——三者共同服务「信任建立」主线，且全部只消费已有架构能力。
2. **P2（一期收尾前）**：F3 批量筛选、F5 审批工作台、F6 通知中心、F10 批次推荐与 Pareto 简化视图。
3. 排期原则不变：**每轮只解一个主矛盾**；功能开发不得挤占 R2 三件套（DDL / 回放框架 / walking skeleton）的资源。
