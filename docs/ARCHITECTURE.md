## 1. 架构目标、约束与质量属性

架构设计必须先承认化工配方 AI 与通用互联网 AI 的根本差异，否则技术选型会系统性失准。

### 1.1 五条硬约束

| 编号 | 约束 | 对架构的直接影响 |
|---|---|---|
| C1 | **样本稀缺且昂贵**：单个配方从配料、固化到全性能测试常需数天至数周，历史可用标注常为 10²–10³ 量级，且分布高度偏向「成功配方」 | 禁止以深度学习为默认主干；必须设计主动学习、迁移学习、多保真度融合、文献弱标注；每次实验推荐都要有信息价值评估 |
| C2 | **强合规与高敏感**：配方即企业核心资产，泄露即商业损失 | 私有化优先、气隙可交付、数据分级、全链路审计、对外脱敏；不能依赖任何需出网的 SaaS 能力 |
| C3 | **决策需要可信理由**：工程师不会采纳无法解释的黑盒结果 | 可解释性与不确定性是「一等公民」，与预测值同级返回；物理一致性校验前置；OOD 必须拒答或降权 |
| C4 | **多目标强冲突**：导热↑ 常致粘度↑、绝缘性↓；性能目标之间是 Pareto 关系而非单目标最优化 | 优化服务输出前沿而非单点；目标约束需可配置；UI 必须支持交互式权衡 |
| C5 | **数据异构且脏**：历史 Excel、ELN 自由文本、测试仪器原始曲线、文献表格、专利权利要求并存 | 数据接入层需要 schema 映射 + 单位归一 + 质量规则引擎；「配比总和=100%」只是数十条规则中最简单的一条 |

### 1.2 质量属性优先级（冲突时的裁决顺序）

1. **数据安全与可审计性**（不可妥协）
2. **结果可复现与可追溯**（模型版本、特征版本、数据快照三位一体）
3. **可解释性与校准度**（宁可给出更宽的置信区间，也不要虚假精确）
4. **闭环有效性**（每轮实验是否真的降低了不确定性）
5. **吞吐与延迟**（在线推理 P95 < 2s；离线批量 10⁵ 配方/小时）
6. **功能广度**（放最后，二期以后再扩）

> 这条排序是本架构最重要的隐藏设计决策：当「上一个新模型」与「保证每条预测可追溯到训练数据范围」冲突时，选后者。

## 2. 总体架构（分层 + 三条主线）

### 2.1 逻辑分层（保留 v1 骨架，补齐边界）

```
┌───────────────────────────────────────────────────────────────────────┐
│ L1 用户交互层  Web 工作台 / 逆向设计台 / 实验台 / 知识中心 / 管理控制台 │
│                多租户隔离 · 角色视图 · 交互式 Pareto 图               │
└───────────────────────────────┬───────────────────────────────────────┘
                                │ HTTPS / REST + WebSocket（任务进度）
┌───────────────────────────────▼───────────────────────────────────────┐
│ L2 应用服务层（无状态，可水平扩展）                                    │
│  预测服务 · 优化服务 · 主动学习服务 · 生成服务                        │
│  实验与项目服务 · 权限与审计服务 · 知识问答服务                       │
│  ── 编排网关：鉴权 / 限流 / 幂等 / 请求追踪 / 结果缓存 ──              │
└──────────┬─────────────────────────────────┬──────────────────────────┘
           │ 同步推理 gRPC                     │ 异步任务（消息总线）
┌──────────▼──────────────────┐   ┌──────────▼───────────────────────────┐
│ L3 AI 核心引擎               │   │ L3' 知识与数据中台                   │
│  特征工厂（版本化/可复现）   │◄──┤  配方库 · 性能库 · 原材料库          │
│  多任务预测 + 不确定性       │   │  文献/专利库 · 知识图谱 · 向量索引    │
│  优化 / 主动学习 / 生成      │   │  版本 · 血缘 · 质量规则 · 多保真度    │
│  模型生命周期与注册中心      │   └──────────────────────────────────────┘
└──────────┬──────────────────┘
           │
┌──────────▼────────────────────────────────────────────────────────────┐
│ L4 基础设施与集成层                                                    │
│  计算/调度 · 对象存储 · 模型仓库 · 实验仪器与 LIMS/ELN/ERP 适配 · 监控 │
└────────────────────────────────────────────────────────────────────────┘
```

### 2.2 三条贯穿主线（v1 缺失的视角）

分层图只能表达「谁调用谁」，表达不了系统真正运转的方式。补充三条正交主线：

| 主线 | 承载内容 | 关键组件 | 失败模式 |
|---|---|---|---|
| **控制面** | 租户、权限、模型版本、特征版本、灰度策略、审计 | 配置中心 + 模型注册中心 + 策略引擎 | 版本错配导致预测不可复现 |
| **数据面** | 配方向量、特征、预测结果、测试结果、血缘 | Feature Store + 事件总线 + 数据湖 | 训练/推理特征漂移（training-serving skew） |
| **实验面** | 推荐 → 排程 → 执行 → 回写 → 触发重训 | 实验状态机 + 任务编排 + 外部系统适配器 | 反馈长期不闭环，模型停在初始版本 |

> 架构评审时建议用这三条主线逐一走查：任何新需求都必须能回答「它落在哪个面、跨了几个面、跨面的一致性如何保证」。

### 2.3 部署视图（私有化优先）

```
企业内网 / 气隙环境
├── DMZ 区：反向代理、WAF、SSO 对接（可选）
├── 应用区（K8s 通用节点池）
│   ├── 前端静态资源 + BFF
│   ├── L2 应用服务（HPA，无状态）
│   ├── 在线推理服务（CPU 为主，树模型批推理 < 200ms）
│   └── 异步 Worker（Celery：特征计算、批量预测、训练触发）
├── AI 区（GPU 节点池，带污点/容忍，按需启停）
│   ├── GNN 训练 / 生成模型训练
│   └── 大模型推理（私有化 LLM，用于知识中心）
├── 数据区（StatefulSet / 外部托管）
│   ├── PostgreSQL（主数据 + 元数据 + 审计）
│   ├── MinIO（原始曲线、文档、模型产物、数据快照）
│   ├── Neo4j（图谱） + Qdrant（向量）
│   └── Redis（缓存 + 队列） / RabbitMQ（可靠任务）
└── 集成区：LIMS / ELN / ERP 适配器（单向出网白名单，或摆渡机导入）
```

**气隙交付要求**：全部镜像、模型权重、依赖包以离线 bundle 交付；许可证与漏洞扫描在构建侧完成；不依赖任何运行时外网校验；升级通过离线包 + 校验和完成。

## 3. 领域模型与核心数据设计

这是 v1 最薄弱、却最决定项目成败的一节。化工配方数据的建模错误，后期几乎无法靠算法弥补。

### 3.1 核心实体关系

```
Material（原材料）
   │ 1:N
   ├──► MaterialBatch（批次、供应商、COA 物性、到货日期）
   │
Formula（配方，聚合根）
   ├── FormulaVersion（版本号、变更原因、审批状态）
   ├── FormulaComponent（组分 + 质量份/phr + 角色：主体树脂/固化剂/填料/助剂）
   │        └── 引用 Material / MaterialBatch
   ├── ProcessCondition（混胶温度、固化温度/时间/压力、后固化、涂布厚度…）
   └── 1:N ──► Experiment（实验任务、DoE 批次、执行人、设备）
                    └── 1:N ──► TestResult（原始曲线 + 提取指标 + 测试标准）
                                     └── 关联 metric_definition 定义
Model / FeatureSet / DatasetSnapshot：通过 DataLineage 与上述实体关联
```

### 3.2 核心表结构（节选，PostgreSQL）

| 表 | 关键字段 | 设计要点 |
|---|---|---|
| `formula` | `id, tenant_id, project_id, code, current_version_id, confidentiality_level, created_by` | 配方与版本分离；`current_version_id` 只作指针，历史不可变 |
| `formula_version` | `id, formula_id, version_no, parent_id, change_reason, approval_status, snapshot_json` | 追加写（append-only），`snapshot_json` 固化当次完整配方，避免 JOIN 还原出错 |
| `formula_component` | `version_id, material_id, batch_id, mass_part, role, equivalent_ratio` | `mass_part` 用 phr/质量份并以 `DECIMAL` 存储，禁用浮点避免配比漂移 |
| `process_condition` | `version_id, step_seq, param_key, value, unit, normalized_value` | 键值 + 量纲归一；`normalized_value` 由单位换算服务写入，供特征层直接消费 |
| `material` | `id, cas_no, smiles, supplier, func_group, functionality, density, price, availability` | SMILES/CAS 用于分子描述符；`availability` 与 `price` 供约束检查 |
| `material_batch` | `id, material_id, supplier, lot_no, coa_ref, received_at, expiry, props_json` | 批次物性是 point-in-time 特征的来源；禁止用最新批次回填历史配方（§17.2 标签泄漏陷阱） |
| `experiment` | `id, batch_id, formula_version_id, doe_design_id, state, planned_at, finished_at, operator_id` | `state` 为显式状态机（见 §6.1） |
| `test_result` | `id, experiment_id, metric_id, raw_ref(MinIO), value, unit, test_standard, fidelity, qc_flag` | `fidelity` 标记实验/仿真/文献三档；`qc_flag` 决定是否可入训练集 |
| `metric_definition` | `code, name, unit, direction(higher_better/lower_better/target), acceptable_range` | 优化目标的方向与区间必须由业务在此定义，禁止硬编码在模型代码里 |
| `feature_set` | `id, version, definition_hash, generator_version, created_at` | `definition_hash` 保证特征定义可复现 |
| `model_registry` | `id, model_type, version, feature_set_id, dataset_snapshot_id, metrics_json, stage` | 模型与特征版本、数据快照强制三元组绑定 |
| `recommendation` | `id, batch_id, candidates_json, scores_json, model_version, constraint_set_version, input_snapshot_id, state, decided_by, decided_at` | 推荐/采纳/拒绝/取消结构化留存，是采纳率指标与约束库修正的依据（§6.1、§15.3、§18.5） |
| `lineage_edge` | `src_type, src_id, dst_type, dst_id, relation` | 支撑「该预测用了哪些配方/哪版模型」的反向追溯 |
| `audit_event` | `id, actor, tenant, action, object_ref, before_hash, after_hash, ts` | 只追加、分区存储、不可篡改（可选追加哈希链） |

> 另有 `doe_design`、`quality_rule`、`prediction_log`、`constraint_set` 等支撑表，随 B01 的 DDL 一并给出。

### 3.3 化工领域约束（质量规则引擎）

按严重程度分三级，**阻断级**规则不通过的数据禁止进入训练集：

| 级别 | 规则示例 | 处理 |
|---|---|---|
| 阻断 | 配比总和 ≠ 100%（或 phr 基准不一致）；负值与空值；单位缺失；同一配方同批次重复录入 | 拒绝导入，生成 QC 报告 |
| 阻断 | 当量比/官能团比超出化学合理区间；固化剂与树脂官能度不匹配；固化制度低于体系反应所需温度窗口（如固化剂活化/分解温度） | 拒绝，提示规则编号 |
| 告警 | 组分物性缺失、批次 COA 过期、测试标准与项目基线不一致、指标超出历史 3σ | 允许入库但打 `qc_flag`，训练时降权或排除 |
| 提示 | 命名不规范、备注含自由文本疑似关键信息、同一文献多版本 | 进入人工复核队列 |

另需**单位与量纲归一**：导热系数 W/(m·K)、体积电阻率 Ω·cm、粘度 mPa·s、Tg °C、剪切强度 MPa 等统一到基准单位，保留原始值与原始单位以便审计；性能测试条件（温度、湿度、试样厚度、固化制度）必须作为特征而非元数据，否则同配方不同条件会被误判为标签噪声。

### 3.4 多保真度数据融合

| 保真度 | 来源 | 规模 | 用途 | 建模方式 |
|---|---|---|---|---|
| F0 低 | 文献/专利抽取、公开数据库 | 10³–10⁴ | 预训练、先验、相似配方检索 | 弱标签、区间标签、仅作排序/先验 |
| F1 中 | MD/FEA 仿真、经验公式、半经验估算 | 10⁴–10⁵ | 扩充覆盖、探索边界 | 作为辅助任务或偏差校正项 |
| F2 高 | 实测（企业自有） | 10²–10³ | 最终校准与决策依据 | 主任务、高样本权重 |

推荐 **multi-fidelity 结构**：低保真数据学习全局趋势，实测数据学习残差校正（Δ-learning）或作为 co-kriging 的高保真层。禁止简单拼接后一视同仁地训练——那会让模型被文献中的系统性偏差带偏，且无法给出可信的不确定性。

### 3.5 数据版本与血缘

每次训练生成不可变 `dataset_snapshot_id`（内容哈希 + 时间戳 + 规则版本）。每条预测结果必须携带 `model_version + feature_set_version + dataset_snapshot_id`，以支持「客户质疑某次预测时，能完整还原当时的输入、特征、模型与训练数据范围」。这是 v1「模型水印与溯源」的落地实现。

## 4. 服务边界与接口契约

### 4.1 服务清单与边界

| 服务 | 职责 | 不负责 | 状态 |
|---|---|---|---|
| `prediction-svc` | 配方特征化、多任务推理、不确定性 + 解释生成 | 不做优化、不写库 | 无状态 |
| `optimization-svc` | 多目标优化、Pareto 前沿、约束检查 | 不直接调模型（经 prediction-svc） | 任务态 |
| `active-learning-svc` | 信息增益计算、下一批实验点推荐、批次去冗余 | 不决定实验排程 | 任务态 |
| `generation-svc` | 条件生成、逆向候选、可执行性过滤 | 不保证性能达标（须经预测验证） | 任务态 |
| `experiment-svc` | 实验状态机、DoE 编排、结果回写、LIMS/ELN 同步 | 不做质量判定（交 QC 服务） | 有状态 |
| `data-hub-svc` | 主数据、版本、血缘、质量规则、快照 | 不做特征计算 | 有状态 |
| `knowledge-svc` | 文献检索、RAG 问答、图谱查询 | 不做性能预测 | 有状态 |
| `auth-audit-svc` | 鉴权、数据分级、脱敏、审计 | 不承载业务逻辑 | 有状态 |
| `model-lifecycle-svc` | 训练编排、评估门禁、注册、灰度、回滚、漂移 | 不承载在线流量 | 控制面 |

**边界原则**：只有一个服务拥有写权限（`data-hub-svc` 写主数据，`experiment-svc` 写实验与结果），其余通过 API/事件消费，避免多头写入导致血缘断裂。

### 4.2 同步 / 异步切分

| 场景 | 通道 | 理由 |
|---|---|---|
| 单配方实时预测（< 2s） | 同步 REST/gRPC | 交互式工作台需要即时反馈 |
| 批量虚拟筛选（10⁴–10⁶） | 异步任务 + WebSocket 进度 | 长任务不可占用请求线程 |
| 贝叶斯优化 / 生成候选 | 异步任务 | 迭代式搜索，分钟级 |
| 训练、重训、评估 | 异步 + GPU 队列 | 资源密集、需排队与优先级 |
| 实验结果回写 → 触发重训 | 事件驱动 | 解耦，允许失败重放 |

### 4.3 关键 API 契约（示意）

```http
POST /api/v1/predict
{
  "formula": { "components": [...], "process": {...} },
  "targets": ["thermal_conductivity", "volume_resistivity", "lap_shear"],
  "options": { "explain": true, "calibrate": true, "ood_check": true }
}
→ 200
{
  "request_id": "...",
  "predictions": [
    { "metric": "thermal_conductivity", "value": 1.42, "unit": "W/(m·K)",
      "interval": { "p10": 1.21, "p90": 1.63, "confidence": 0.9 },
      "ood_flag": false,
      "explanation": { "method": "shap", "top_factors": [...] } }
  ],
  "provenance": { "model_version": "...", "feature_set": "...",
                  "dataset_snapshot": "...", "served_at": "..." }
}
```

设计要点：
- **不确定性是必返字段**，不是可选开关；`ood_flag=true` 时前端必须显式提示「超出训练分布，结果仅供参考」。
- **provenance 必返**，且写入审计日志，与 §3.5 呼应。
- 所有 POST 支持 `Idempotency-Key`；异步任务返回 `task_id`，状态机为 `queued → running → succeeded / failed / cancelled`，失败保留中间产物供排查。
- 版本化路径 `/api/v1`，破坏性变更升版本，旧版本至少并行 2 个迭代周期。

### 4.4 一致性策略

跨服务不引入分布式事务：采用**事件溯源 + 最终一致**。例如「实验结果回写」发布 `ExperimentCompleted` 事件，由 QC 服务消费并校验，通过后再发布 `DataAccepted`，训练编排消费后者。每个事件携带 `snapshot_id` 与幂等键，重放不产生重复样本。对账任务每日比对事件流与库内状态，告警不一致。

## 5. AI 核心引擎深化

v1 列出了算法清单；本节回答「在小样本、强合规、需可信的化工场景下，这些算法怎么真正跑通」。

### 5.1 特征工厂：可复现优先于丰富度

| 特征族 | 生成方式 | 注意点 |
|---|---|---|
| 组分物性统计 | 质量份加权和/极值/方差（密度、官能度、分子量、导热系数…） | 缺失值需显式标记并生成缺失指示位，禁止隐式填 0 |
| 分子描述符 | RDKit / Mordred，对树脂、固化剂、单体分别计算后聚合 | 描述符高维且共线，须做相关性剪枝 + 稳定的固定选择器 |
| 结构编码 | GNN / 预训练分子编码器 | 仅在有足量数据或可迁移预训练权重时启用；否则作为二期能力 |
| 交互特征 | 当量比、官能团比、填料体积分数、界面面积估算、极性匹配 | **领域知识驱动的交互特征在小样本下往往比自动交叉更有效** |
| 工艺特征 | 归一化后的温度/时间/压力，及组合项（如等效固化度） | 必须含测试条件（§3.3） |
| 配方指纹 | 组分集合哈希 / 相似度向量 | 用于 OOD 检测与去重 |

**工程约束（最容易出问题的地方）**：
- 训练集与在线推理共用**同一份特征定义代码与同一 `feature_set_version`**，禁止训练脚本里另写一套特征逻辑。
- 特征计算产物落 Feature Store，训练时按 `point-in-time` 取快照，防止用到「未来才知道」的原材料批次信息。
- 任何特征变更都生成新版本，模型必须重新训练才能使用，不允许「悄悄改特征」。

### 5.2 预测模型：务实的主干选择

**推荐分层策略（而非单一模型）**：

| 层 | 模型 | 理由 |
|---|---|---|
| 基线 / 主力 | LightGBM / XGBoost 多任务（每个指标一个 head，共享特征） | 100–1000 样本量级最稳、训练快、可解释、CPU 可服务 |
| 小样本指标 | Gaussian Process / 分位数回归森林 | 天然给出不确定性，适合昂贵指标 |
| 结构信息 | GNN（预训练 + 微调） | 数据量或迁移条件具备后再上，与树模型做 stacking |
| 融合 | 多保真度残差校正（§3.4） | 把文献/仿真知识注入而不污染实测标签 |

**不确定性必须校准**：分位数回归 / 深度集成给出的区间常过于自信。上线前用 **conformal prediction** 在留出集上做校准，验收指标是「90% 区间的实际覆盖率 ≥ 88%」，而不是只看点预测 RMSE。未校准的不确定性会直接误导主动学习的采集函数。

**物理与机理一致性**：引入单调性/符号约束（如填料体积分数上升对导热的正向趋势、交联密度上升对 Tg 的正向趋势），可用单调约束 GBDT 或对违反方向的结果打标复核。模型给出「物理上不可能」的组合时，应触发人工复核而非直接推送给实验。

**解释不等于 SHAP**：配方组分存在严重共线性（填料增加必然导致树脂占比下降），SHAP 会把归因在相关特征间任意分配。建议同时提供：① 基于领域分组的归因（按「填料体系 / 固化体系 / 工艺」聚合）；② 相似历史配方案例（case-based 解释，工程师最易接受）；③ 局部扰动敏感度。SHAP 仅作补充，且必须附共线性提示。

### 5.3 优化与主动学习：防止「高维退化」

- 配方空间是**离散 + 连续混合、带约束、变量数常 10–30** 的空间，标准贝叶斯优化在此会退化。对策：先降维到隐空间（生成模型的潜变量 / PCA）或采用信任域贝叶斯优化（TuRBO）、结构化核；对离散组分数使用组合核。
- 采集函数不能只用 EI：需叠加**不确定性采样 + 多样性（批次内去冗余）+ 成本权重**（某些测试极贵）。推荐批次大小为 4–8，与实验班次产能对齐。
- 约束前置：原材料可得性、成本上限、工艺窗口、安全/环保法规（如 REACH/RoHS 禁限用物质）在生成候选时即过滤，避免推荐「做不出来」的配方——这是工程师对 AI 平台失去信任的首要原因。
- **输出 Pareto 前沿而非单一最优**，由工程师在交互式图上按当期业务优先级选择，选择行为本身记录为偏好数据，用于后续目标权重学习。

### 5.4 生成与逆向设计

条件生成（cVAE / Diffusion / LLM 辅助）在化工小样本下风险最高，定位为**候选生成器而非决策器**：生成 → 约束过滤 → 预测服务验证 → 仅把「预测达标且不确定性可控」的候选交给优化服务排序。所有生成候选标注 `synthetic` 来源，禁止直接写入训练标签。LLM 只用于配方解读、实验方案草拟、失败原因归纳，且必须走私有化部署与 RAG 约束，禁止让 LLM 直接输出数值性能结论。

### 5.5 模型生命周期（控制面）

```
数据快照冻结 → 特征版本锁定 → 训练（可复现随机种子/环境镜像）
  → 评估门禁 → 注册(staging) → 影子流量 → 灰度(5%→25%→100%)
  → 生产 → 漂移监控 → 触发重训 / 自动回滚
```

**评估门禁（不达标不允许注册）**：
| 门禁 | 阈值示例 |
|---|---|
| 各指标相对基线的改进 | 不得劣化超过 2%，至少 1 个指标显著改进 |
| 区间覆盖率 | 90% 区间实测覆盖 ≥ 88% |
| OOD 检出召回 | ≥ 85%（用留出体系做负例） |
| 物理一致性违规率 | ≤ 1% |
| 可复现性 | 同代码+同快照重训，指标差异 < 1% |

**漂移监控三路**：输入漂移（新配方指纹与训练分布距离）、性能漂移（回写实测 vs 预测残差滑动窗口）、概念漂移（原材料供应商/批次变更、测试标准变更）。触发策略分级：轻度→告警并建议重训；残差持续超阈值→自动冻结该指标推荐并回滚到上一稳定版本。

## 6. 闭环的工程实现（v1 只画了箭头）

「预测 → 推荐 → 实验 → 反馈」若没有状态机和责任边界，实际会停在「推荐完没人做」或「做了没回写」。

### 6.1 实验状态机

```
RECOMMENDED → REVIEWED（工程师确认/调整）→ SCHEDULED → IN_PROGRESS
   → COMPLETED → QC_PENDING → ACCEPTED → [触发重训评估]
   ├→ REJECTED（数据不合格，记录原因，进入失败样本库）
   └→ CANCELLED（记录取消原因，用于分析推荐可执行性）
```

每个状态迁移写入审计与时间戳，形成**推荐采纳率、实验完成周期、QC 通过率**三条运营指标。推荐被拒绝/取消的原因是最有价值的数据：它反映约束建模是否贴近现实。

### 6.2 反馈延迟与样本权重

实验结果常滞后数天至数周，闭环必须容忍长延迟：
- Pending 实验在优化时作为「已占用点」参与采集函数的去冗余，避免重复推荐同类配方。
- 新回写样本按 `fidelity`、测试标准一致性、时间衰减赋权；近期高保真实测权重最高。
- 采用增量训练 + 定期全量重训：增量用于快速吸收新数据，全量重训防止增量累积偏差。
- **防灾难性遗忘**：新数据常集中在近期探索的局部区域，直接微调会让模型在历史区域失真。保留回放缓冲区（历史代表性样本）或使用正则化约束，并在全量门禁中检查历史留出集指标不劣化。

### 6.3 在线 / 离线双通道

| 通道 | 入口 | 计算 | 产出 |
|---|---|---|---|
| 在线交互 | 工作台单配方 | 同步推理，秒级 | 预测 + 区间 + 解释 + 溯源 |
| 离线批量 | CSV / API 批量、虚拟筛选 | Worker 分片 + 缓存 + 断点续算 | 排序清单 + 分布报告 + OOD 统计 |

两通道**共用同一模型服务与特征版本**，仅调度方式不同，避免「批量筛出来的结果与工作台单点预测不一致」这类信任事故。

### 6.4 闭环有效性的度量

不看「模型 RMSE 又降了多少」，而看：达到目标性能所需**实验轮次下降比例**、单位周期**命中配方数**、**推荐采纳率**、**从目标下达到候选确认的时长**。这四项才是客户能感知的价值，也是 §12 验收指标的依据。

## 7. 知识与数据中台深化

### 7.1 质量规则引擎（§3.3 的落地）

规则以声明式配置（`rule_id, level, expression, scope, message`）存储，支持按项目/材料体系启用不同规则集；规则版本随数据快照冻结。导入时生成 QC 报告（通过/告警/阻断明细 + 行号），支持修正后重导入，全过程留痕。

### 7.2 RAG 与知识图谱的职责边界

| 能力 | 承载 | 原因 |
|---|---|---|
| 「文献里怎么说的」「专利相似配方」「失败原因分析」 | 向量库 + RAG（Qdrant + 私有 LLM） | 面向非结构化文本，需要语义检索与生成 |
| 「材料–机理–性能–应用」关系推理、多跳溯源 | 图谱（Neo4j） | 需要显式关系与路径查询 |
| 「这个配方预测性能多少」 | 预测服务 | 结构化数值任务，禁止交给 LLM |

**关键约束**：RAG 答案必须带引用（文献 ID / 页码 / 段落），图谱抽取的「配方–性能」关系必须标注 `fidelity=F0` 与抽取置信度，且只能作为先验或检索线索，不得直接充当实测标签。抽取流水线（PDF 解析 → 表格还原 → 实体/关系抽取 → 人工抽检）需要抽检率与准确率指标，否则知识库会静默污染。

### 7.3 血缘实现

`lineage_edge` 由各写服务在事件消费时自动追加，形成有向图。对外提供两个方向的查询：「这条预测用到了哪些配方/文献」（正向审计）与「这份配方被哪些模型、哪些预测、哪些导出使用过」（反向影响面分析，用于配方泄密或数据撤回场景）。

## 8. 安全、合规与多租户

### 8.1 数据分级矩阵

| 级别 | 定义 | 可见范围 | 导出 | 脱敏 | 建模可用性 |
|---|---|---|---|---|---|
| L0 公开 | 公开文献、物性常数 | 全租户 | 允许 | 无需 | 可用 |
| L1 内部 | 通用配方模板、脱敏历史数据 | 同租户内全员 | 审批后 | 可选 | 可用 |
| L2 机密 | 在研配方、实测性能、客户项目 | 项目组成员 | 需双人审批 + 水印 | 必须 | 仅项目内模型 |
| L3 核心 | 核心树脂体系、关键客户配方 | 白名单人员 | 原则上禁止 | 强制 + 组分泛化 | 默认不跨项目 |

### 8.2 权限模型（RBAC + ABAC）

角色（系统管理员 / 研发主管 / 配方工程师 / 实验员 / 只读审计员）定义**操作**权限；ABAC 基于 `tenant_id + project_id + confidentiality_level + purpose` 判定**数据**权限。二者取交集，默认拒绝。特别地：
- 训练任务的数据读取权限按调用者身份裁剪，**不允许通过模型间接泄露高密级配方**（跨密级训练需显式审批并生成隔离模型实例）。
- 导出/打印/批量 API 视为高风险动作，强制审批 + 水印 + 审计；批量接口额外做速率与条数限制，防止拖库。

### 8.3 脱敏与审计

脱敏策略分级：组分名泛化（具体牌号 → 类别）、配比区间化（±5%）、工艺参数桶化、去除供应商与批次标识；脱敏后数据仅用于对外演示与跨项目基线，不可反推。审计事件覆盖预测、导出、登录、权限变更、模型发布、训练数据范围变更，含 `before_hash/after_hash`，独立存储且对业务库只读，保留周期按客户合规要求配置（建议 ≥ 3 年）。

### 8.4 模型水印与溯源

每条预测结果（API 响应、导出文件、报告）嵌入不可见但可校验的 `provenance` 签名；导出文件附加可见水印（用户、时间、租户）。配合 §3.5 的三元组版本，形成「结果 → 模型 → 特征 → 数据快照 → 原始配方」的完整证据链。

### 8.5 私有化与气隙

默认完全本地部署；所有第三方组件使用可离线分发的开源许可；私有 LLM 权重本地加载；不启用任何遥测上报。若客户要求跨站点同步，采用离线介质摆渡 + 校验和，不建立持久出网通道。

## 9. 基础设施、部署与可观测性

### 9.1 技术栈（沿用 v1 并补充取舍）

| 层级 | 选型 | 补充决策 |
|---|---|---|
| 前端 | Vue3 + TypeScript + ECharts / Plotly | Pareto 图与不确定性区间需要交互能力，优先 ECharts；大批量散点用 WebGL 层 |
| 后端 | Python FastAPI + Celery | 训练/推理同语言栈，降低特征逻辑重复实现风险；BFF 可选 Node 做 SSR |
| 特征/模型 | RDKit、Mordred、PyG、LightGBM/XGBoost、BoTorch | 树模型 CPU 服务；GNN/生成模型才上 GPU |
| 存储 | PostgreSQL + MinIO + Neo4j + Qdrant | 四类存储按查询模式分工，避免用一种数据库硬扛全部 |
| 模型仓库 | MLflow（+ DVC 管理数据快照） | MLflow 管模型与指标，DVC/内容寻址管数据，避免大文件入 Git |
| 队列 | Redis（缓存/轻量）+ RabbitMQ（可靠任务） | 训练与批量任务要求至少一次投递与死信队列，用 RabbitMQ |
| 部署 | Docker + K8s + Helm，GPU 节点池 | 离线用 K3s / 单节点版降低客户运维门槛 |
| 监控 | Prometheus + Grafana + Loki + OpenTelemetry | 业务指标与模型指标分看板 |

### 9.2 SLI / SLO

| 指标 | 目标 |
|---|---|
| 在线预测可用性 | ≥ 99.5%（工作时段） |
| 在线单配方 P95 延迟 | < 2s（含解释） |
| 批量吞吐 | ≥ 10⁵ 配方/小时（树模型，16 vCPU） |
| 异步任务可恢复率 | 100%（断点续算 / 重放） |
| 预测溯源完整率 | 100% |
| 审计事件丢失率 | 0 |
| 漂移告警平均发现时间 | < 1 个数据回写周期 |

### 9.3 三类监控看板

1. **系统**：QPS、延迟、错误率、队列积压、GPU 利用率、存储水位。
2. **模型**：输入漂移距离、残差趋势、区间覆盖率、OOD 比例、各指标门禁通过率、当前生效版本与灰度比例。
3. **业务闭环**：推荐采纳率、实验轮次、命中率、QC 阻断原因分布、待回写实验积压（**最容易被忽略但最关键**）。

### 9.4 容量与成本（立项估算口径）

按单租户 500 配方版本/年、200 实验批次/年、指标 6–8 个估算：结构化数据 < 100 GB/年，原始曲线与文档 0.5–2 TB/年；树模型训练 分钟级/CPU，在线推理无需常驻 GPU；GPU 仅在二期生成模型/私有 LLM 后按需申请。据此可给出「**MVP 阶段零 GPU 常驻成本**」这一对客户很有说服力的结论，把预算集中在数据治理与实验闭环上。

## 10. 关键架构决策记录（ADR 摘要）

| # | 决策 | 备选 | 取舍理由 |
|---|---|---|---|
| ADR-01 | 闭环优先，不做一次性黑盒预测 | 只交付预测 API | 配方数据稀缺，价值来自「用更少实验收敛」，而非单次预测精度 |
| ADR-02 | 主力模型用树模型，GNN 后置 | 直接上 GNN / 深度多任务 | 10²–10³ 样本下树模型更稳、可解释、无需 GPU；GNN 留待数据积累或迁移 |
| ADR-03 | 私有化 / 气隙优先 | 公有云 SaaS | 配方为核心资产，C2 不可妥协；也利于对外输出「可信交付」能力 |
| ADR-04 | 特征定义单一来源 + 版本锁定 | 训练/推理各自实现 | 防止 training-serving skew，保证可复现 |
| ADR-05 | 不确定性用 conformal 校准后必返 | 只返回点预测 / 原始分位数 | 未校准区间会误导主动学习并损害信任 |
| ADR-06 | 多保真度分层建模，文献仅作弱先验 | 全部数据混合训练 | 避免文献系统偏差污染实测标签 |
| ADR-07 | 配方与版本分离、快照不可变 | 主表覆盖更新 | 血缘与审计的前提，且历史还原成本低 |
| ADR-08 | 跨服务最终一致 + 事件溯源 | 分布式事务 | 长周期实验场景无法承受同步事务；重放与对账更实用 |
| ADR-09 | RBAC + ABAC 且禁止跨密级训练 | 仅 RBAC | 防止通过模型参数间接泄露高密级配方 |
| ADR-10 | 输出 Pareto 前沿而非单一最优 | 单目标加权求和 | 目标强冲突，权重应由工程师按当期业务决定 |
| ADR-11 | 生成模型定位为候选生成器 | 直接由生成模型给最终配方 | 小样本下生成结果不可靠，必须经预测验证与约束过滤 |
| ADR-12 | MVP 不上知识图谱 / 私有 LLM / LIMS 深度对接 | 一期全上 | 数据治理与闭环才是瓶颈，过早引入会拖长验证周期并放大集成风险 |
| ADR-13 | 解释为可降级项，超时返回部分响应 | 解释与预测同步强绑定 | 解释耗时约为推理 5 倍，强绑定会击穿 P95 且拖垮可信功能 |
| ADR-14 | 语义断言 + 金丝雀配方集防静默失败 | 只监控服务可用性 | AI 最危险的故障是「返回了格式正确的错答案」，不会触发任何可用性告警 |
| ADR-15 | 共享 schema + PostgreSQL RLS，且离线链路同样走 RLS | 仅应用层 ABAC 过滤 | 应用层漏写 WHERE 或训练脚本高权限直读，会导致跨租户/跨密级泄露 |
| ADR-16 | 事件采用统一信封 + 幂等键 + 每日对账 | 各服务自定义消息格式 | 长周期实验下重复投递与乱序不可避免，无契约则无法重放与审计 |
| ADR-17 | 用离线回放验证主动学习有效性 | 上线后在线 A/B 验证 | 单轮实验数天到数周，在线 A/B 统计功效不足且先烧掉客户实验预算 |
| ADR-18 | 迁移采用扩展-收缩、三层独立回滚 | 原地改列 / 整体回滚 | 气隙环境无法远程救场，回滚能力必须内建在交付包中 |

> 这些 ADR 建议在对外白皮书中以「方法论与交付保障」章节呈现：客户买的不只是功能，更是**经过取舍的、能承担责任的判断**。

## 11. 演进路线与范围控制

### 一期（MVP，验证闭环价值）

**做**：多租户与权限；数据导入、单位归一、QC 规则（阻断级）；Feature Store 基础版 + 版本化特征工厂；多任务 LightGBM + conformal 区间 + 分组解释 + OOD 检测；信任域贝叶斯优化（单目标/Pareto 简化版）+ 约束过滤；实验状态机与结果回写（人工/CSV 为主）；Web 工作台（配方预测、Pareto 图、实验列表）；审计与溯源。

**不做**：生成模型、GNN、知识图谱、私有 LLM、LIMS 双向深度集成、跨站点同步。

**一期真正的验收门槛**：不是「模型上线」，而是**跑通至少 2 轮完整闭环**——推荐被采纳、实验完成、结果回写、模型更新、下一轮推荐发生变化。

### 二期（闭环深化与知识增强）

主动学习全闭环（批次去冗余、成本权重、pending 占用）；增量训练 + 防遗忘；漂移自动触发重训与回滚；LIMS/ELN 双向对接（幂等 + 对账）；知识中心（RAG + 私有 LLM，带引用）；多保真度融合；GNN 在数据量达标后以 stacking 方式引入。

### 三期（平台化与扩展）

多材料体系（涂料、密封胶、电子封装）以「配方 schema + 规则集 + 指标定义」配置化扩展，而非改代码；仿真（MD/FEA）深度集成；数字孪生材料卡片输出；供应链价格/库存联动约束；跨项目联邦式建模（在不移动原始配方前提下共享模型能力）；对外能力开放平台。

**扩展性原则**：新体系接入的成本应体现在**配置**（指标定义、规则集、特征模板、目标方向），而不是新增一套服务。这是判断架构是否成立的关键测试。

## 15. 运行期视图与关键时序

### 15.1 4+1 视图覆盖矩阵

| 视图 | 回答的问题 | 承载位置 | v2.0 状态 |
|---|---|---|---|
| 逻辑视图 | 有哪些组件、职责与边界 | §2.1、§4.1 | 已覆盖 |
| 物理视图 | 部署拓扑、网络边界、气隙约束 | §2.3、§9 | 已覆盖 |
| 开发视图 | 代码如何组织、依赖方向、构建产物 | §18.1 | 缺失，v2.1 补 |
| 进程视图 | 运行时进程/队列/并发、超时与资源隔离 | §15.2–§15.4 | 缺失，v2.1 补 |
| 场景视图 | 关键用例如何串起组件、失败点在哪 | §15.3、§6 | 仅有流程箭头，v2.1 补时序 |

> 评审常见误区：把分层图当成完整架构。分层只回答「谁调用谁」，不回答「并发多少、超时怎么传导、某个环节挂了系统退化成什么」。这部分缺口往往是上线后第一次事故的位置。

### 15.2 进程模型、队列隔离与超时预算

| 组件 | 进程模型 | 并发与隔离约束 | 失败语义 |
|---|---|---|---|
| 网关 / BFF | 无状态多副本，异步 IO | 按租户限流，批量任务单独配额 | 快速失败并返回明确错误码 |
| `prediction-svc` | 无状态，CPU 密集 | 特征计算走进程池，禁止在事件循环内执行；服务内特征计算与推理解耦 | 部分响应（见 §15.3） |
| 在线推理服务 | 模型常驻内存 | 按 `model_version` 双缓冲加载，切版本不留空窗 | 校验失败则就绪探针不通过 |
| 异步 Worker | Celery 独立队列 | `feature` / `batch` / `train` / `export` 四队列隔离，防止训练饿死交互任务 | 幂等重试 + 死信队列 |
| 训练 Job | K8s Job，GPU 节点池 | 可抢占、设 TTL、支持断点续训 | 保留中间产物，绝不自动发布 |
| Feature Store 客户端 | 本地缓存 + 版本校验 | 缓存键含 `feature_set_version`，版本不匹配即失效 | 不允许用旧特征喂新模型 |

**一次带解释的在线预测，总预算 2s（P95）**：

| 环节 | 预算 | 说明 |
|---|---|---|
| 网关鉴权与 ABAC 判定 | 30 ms | 含数据密级裁剪 |
| 配方解析 + 轻量 QC | 50 ms | 只做阻断级规则的子集 |
| 特征计算（缓存未命中） | 400 ms | 命中时约 20 ms |
| 多任务推理 | 150 ms | 树模型，CPU |
| conformal 区间 + OOD + 物理一致性 | 100 ms | 语义断言在此执行 |
| 分组解释与相似案例检索 | 800 ms | **最贵的一环** |
| 溯源封装 + 审计事件（异步） | 50 ms | 不阻塞响应 |
| 网络与编排余量 | 420 ms | 含重试与排队 |

> 关键洞察：**解释比推理贵 5 倍以上**。因此 `explain` 必须是可降级项——超时先返回「预测值 + 区间 + 溯源」，解释异步补齐并标记 `explanation_status=deferred`。把解释做成必选同步项，是守住 P95 最常见的失败原因。

### 15.3 三条关键链路时序与失败点

**链路 A · 单配方同步预测**

1. 网关鉴权，ABAC 判定该用户可见的密级与目标指标范围
2. `prediction-svc` 按 `formula_version_id` 取不可变快照
3. Feature Factory 以锁定的 `feature_set_version` 计算或读缓存
4. 在线推理服务按 `model_version` 双缓冲推理
5. conformal 校准、OOD 检测、物理一致性断言
6. 分组归因 + 相似历史案例检索（可降级）
7. 组装 provenance 三元组，异步发审计事件，返回

| 失败点 | 处置 |
|---|---|
| 特征版本与模型版本不匹配 | **拒绝服务**，不得静默回退旧特征 |
| OOD 命中 | 返回值但强制标记 `advisory_only`，UI 提示不得直接采纳 |
| 物理一致性违规 | 同上，并写入复核队列 |
| 解释超时 | 部分响应 + 异步补齐 |
| 审计写入失败 | 不阻塞响应，但触发告警并要求补偿写入（审计完整率是硬指标） |

**链路 B · 批次推荐（异步）**

1. 提交任务 → 生成幂等键 → `queued`
2. Worker 加载当前模型、**pending 实验占用集**、约束库版本
3. 候选生成/采样 → 可执行性约束过滤 → 批量预测
4. 采集函数打分 + 批次内去冗余 → 输出 Pareto 前沿
5. 写 `recommendation` 记录（推荐理由、模型版本、输入快照、约束库版本）
6. WebSocket 推送完成

> 最容易漏的是第 2 步：实验周期常为数天到数周，若不把「已推荐但结果未回写」的点计入占用集，同一轮会反复推荐近似配方，工程师会立刻判定系统不可用。

**链路 C · 结果回写触发重训（事件驱动）**

1. ELN / 人工录入 → `ExperimentCompleted`
2. QC 服务消费 → 阻断级规则 → `DataAccepted` 或 `DataRejected`
3. 快照服务冻结新 `dataset_snapshot_id`
4. 训练编排判断触发条件（新增样本数 / 残差漂移 / 距上次训练时长，三者取或）
5. 训练 → 评估门禁 → 注册 `staging` → 影子流量 → 灰度
6. 生产版本切换 → `ModelPromoted`

> 门禁不通过时**保持旧版本继续服务**，把失败原因写进模型卡；绝不「为了闭环而上线」。闭环的价值在于收敛，不在于每轮都必须产出新模型。

### 15.4 资源隔离

- 四类队列隔离，训练队列不得抢占在线推理所在节点的 CPU 配额。
- 批量任务按分片执行 + 断点续算，单分片失败可独立重试，不重跑全批。
- 每租户设并发与条数上限，防止一个大批量筛选拖垮其他项目组。
- GPU 节点池按需申请、任务结束释放；MVP 无 GPU 常驻（见 §9.4）。
- 模型版本切换采用双缓冲：新版本加载并预热完成后再原子切换指针，旧版本保留至回滚窗口结束。

## 16. 故障模式、降级与数据一致性

### 16.1 故障模式与影响分析（FMEA）

| # | 组件 / 故障 | 影响 | 检测 | 降级与恢复 |
|---|---|---|---|---|
| F1 | 在线推理服务不可用 | 预测不可用 | 就绪探针 + 错误率 | 切上一稳定版本（热备）；无可用版本时返回 503，**禁止用经验估值冒充预测** |
| F2 | 模型文件损坏或版本错配 | 结果不可信 | 启动时校验哈希与三元组 | 就绪探针不通过，fail-fast，不静默加载 |
| F3 | Feature Store 不可用 | 无法特征化 | 缓存命中率与连接告警 | TTL 内可用缓存但标记 `degraded`；超时后拒绝在线预测 |
| F4 | 解释服务超时 | 响应变慢 | P95 分环节埋点 | 部分响应，`explanation_status=deferred` |
| F5 | OOD / 物理一致性违规 | 误导实验 | 语义断言 | `advisory_only` + UI 强制提示 + 人工复核队列 |
| F6 | 回写数据未过 QC | 污染训练快照 | QC 规则引擎 | 进死信队列 + 人工队列，不进快照 |
| F7 | LIMS/ELN 同步失败 | 数据缺口 | 同步延迟监控 | 本地先落库，指数退避重试 + 幂等键，每日对账兜底 |
| F8 | 训练任务失败 / 被抢占 | 模型未更新 | Job 状态 | 保留种子与中间产物可续训；不自动发布 |
| F9 | 漂移监控误报 | 无谓回滚、版本震荡 | 多窗口一致性 | 轻度只告警；回滚需连续 N 个窗口 + 人工确认 |
| F10 | 气隙升级包校验失败 | 升级中断 | 校验和比对 | 拒绝升级，保持旧版本运行，保留回滚包 |

### 16.2 AI 特有的静默失败（本节是 v2.1 最重要的补充）

传统监控擅长发现「服务挂了」，但 AI 系统最危险的故障是**返回了格式完全正确、数值完全合理、但结论是错的结果**。它不会触发任何告警，却会连续浪费数轮昂贵实验，且往往在验收时才暴露。

| 静默失败来源 | 典型表现 | 对策 |
|---|---|---|
| training-serving skew | 离线指标好、线上偏差大 | §5.1 特征单一来源 + 上线前线上影子对拍 |
| 单位 / 量纲换算错误 | 数值整体偏移一个数量级 | 语义断言中的量纲范围检查 + golden set |
| 测试条件未入特征 | 同配方不同条件被当成标签噪声 | §3.3 强制条件入特征 + 回归用例 |
| 标签口径漂移 | 测试标准换版后残差突然变大 | 指标定义版本化 + 残差按标准分组监控 |
| 特征版本与模型版本错配 | 结果不可复现 | 三元组绑定校验，不匹配即拒绝服务（F2） |
| 校准区间失真 | 覆盖率远低于标称值 | 每次发布用留出集重算覆盖率门禁 |
| 文献弱标签混入实测 | 预测系统性偏向文献值 | §3.4 保真度字段 + 训练快照审计 |
| 约束库过期 | 推荐了已停产原料 | 约束库版本化 + 推荐记录留存 + 采纳率复盘 |

**三层防护**：

1. **语义断言（semantic assertions）**：响应返回前执行——量纲范围、物理可行边界、配比守恒、单调性方向、指标方向一致性。断言失败不静默修正，而是标记并降级。
2. **金丝雀配方集（canary formulas）**：一组性能已知的固定配方，每次模型加载、每次发布、每日定时各跑一遍；偏差超阈值即自动摘除该版本并告警。这是成本最低、见效最快的静默失败检测手段。
3. **双版本对照**：灰度期新旧版本并行推理，比较差异分布；分布突变则阻断发布，而不是只看聚合指标是否变好。

所有断言与金丝雀结果写入审计，形成「该模型当前是否可信」的持续证据链，与 §8.4 的溯源链合并使用。

### 16.3 降级分级（宁可少给功能，不给假答案）

| 级别 | 触发条件 | 系统行为 | UI 表现 |
|---|---|---|---|
| L0 正常 | 无 | 全功能 | 正常 |
| L1 解释降级 | 解释链路超时 | 预测 + 区间 + 溯源照常，解释异步 | 「解释生成中」 |
| L2 推荐停用 | 优化/主动学习链路异常 | 保留预测与历史查询，暂停新推荐 | 推荐入口置灰并说明原因 |
| L3 只读 | 训练/发布链路异常 | 禁用导出、训练、模型发布 | 顶部横幅提示 |
| L4 拒绝决策输出 | 模型可信度证据缺失（金丝雀失败、覆盖率崩塌） | 只展示历史实测数据，不给任何预测数值 | 明确「系统当前不提供决策建议」 |

> 设计原则：降级时**绝不用低可信结果填补功能空缺**。对研发决策系统而言，「少给一个功能」是可接受的，「给一个看起来正常的错答案」是不可接受的——后者会直接消耗实验预算并摧毁信任。

### 16.4 事件目录、投递语义与幂等

§4.4 给出了最终一致的原则，这里给出可实现的契约。事件采用统一信封（CloudEvents 风格）：

```json
{
  "id": "uuid", "source": "experiment-svc", "type": "ExperimentCompleted",
  "spec_version": "1.0", "time": "ISO-8601", "tenant_id": "...",
  "correlation_id": "...", "idempotency_key": "...",
  "schema_version": "1.2", "data": { }
}
```

| 事件 | 发布者 | 主要消费者 | 投递语义 |
|---|---|---|---|
| `FormulaImported` / `FormulaVersionCreated` | data-hub-svc | 特征、血缘、审计 | 至少一次 + 幂等 |
| `ExperimentCompleted` | experiment-svc | QC 服务 | 至少一次 + 幂等 |
| `DataAccepted` / `DataRejected` | QC 服务 | 快照、训练编排、运营看板 | 至少一次 + 幂等 |
| `DatasetSnapshotFrozen` | data-hub-svc | 训练编排 | 至少一次 + 幂等 |
| `ModelTrained` / `ModelPromoted` | model-lifecycle-svc | 在线推理、审计、通知 | 至少一次 + 幂等 |
| `DriftDetected` | 监控 | 训练编排、告警 | 至少一次，允许重复 |
| `ExportRequested` | BFF | 审批、脱敏、审计 | 有效恰好一次（幂等键 + 审批状态机实现） |

**幂等键规范**：`(tenant_id, event_type, aggregate_id, aggregate_version)`；消费者维护已处理键表，重复投递直接返回上次结果。**重试规范**：仅幂等操作可重试，指数退避 + 抖动，最大 5 次后入死信队列；死信必须可人工重放。**对账**：每日比对事件流与投影状态（实验数、快照数、模型版本数、审计条数），差异写入告警并生成对账报告，不允许人工直接改库消除差异。事件 schema 升版本时消费者需兼容至少两个版本。

### 16.5 强一致与最终一致的边界

| 必须强一致（单库事务） | 允许最终一致（事件 + 对账） |
|---|---|
| 权限与数据分级变更 | 实验结果 → 快照 → 训练触发 |
| 模型生产版本指针切换 | 血缘边追加、运营看板指标 |
| 数据快照冻结与内容哈希写入 | LIMS/ELN 双向同步、通知 |
| 审计事件落库 | 向量索引、图谱投影、缓存失效 |

> 判断标准很简单：**涉及「谁能看到什么」和「当前生效的是哪个版本」的，必须强一致**；涉及「数据逐步流转与派生视图」的，可以最终一致。混淆这两类是数据泄露与版本错配的常见根源。

## 17. 可测试性与闭环有效性验证

### 17.1 六层验证矩阵

| 层 | 验证对象 | 手段 | 门禁 |
|---|---|---|---|
| 数据 | 导入、单位归一、QC 规则 | 规则用例集 + 脏数据回放 | 阻断级规则零误放行 |
| 特征 | 定义一致性、point-in-time 正确性 | 训练/推理特征对拍、时间旅行测试 | 特征值逐列一致 |
| 模型 | 精度、校准、OOD、物理一致性 | §5.5 门禁 + golden set + 金丝雀 | 覆盖率 ≥88%、违规率 ≤1% |
| 服务 | 契约、幂等、部分响应、降级 | 契约测试、故障注入、超时注入 | P95 <2s、审计完整率 100% |
| 闭环 | 推荐是否真的减少实验轮次 | **离线回放**（§17.2） | 相对基线轮次下降 ≥30% |
| 安全 | 越权、脱敏、导出、气隙 | 权限矩阵用例、渗透与审计抽查 | 跨密级访问零命中 |

### 17.2 离线回放：不烧实验预算验证主动学习

化工实验一轮要数天到数周，**不可能靠在线 A/B 去证明「主动学习有效」**。可行且必须前置的手法是历史离线回放（historical replay）：

1. 取历史实验序列，按真实时间排序，冻结 T0 时刻「当时可见」的数据（含当时的原材料批次、测试标准、约束库版本）。
2. 用 T0 之前的数据训练「历史模型」，锁定当时的特征版本。
3. 让待评估的推荐策略在候选池中选下一批实验点；**只揭示历史上真实做过的那些实验的标签**，未做过的点不得窥探结果。
4. 沿时间轴逐步推进，记录「首次达到目标性能区间所用实验轮次」与收敛曲线。
5. 与三条基线对比：随机采样、工程师历史真实顺序、单目标贪心。
6. 在多个项目 / 材料体系上重复，给出轮次下降的分布与置信区间，而非单点数字。

**必须防的三个陷阱**：幸存者偏差（历史库只保留成功配方，会让所有策略显得更好）、标签泄漏（用了后来才知道的批次物性或修订后的测试值）、候选池定义过窄（把「恰好做过的好配方」当候选池，效果虚高）。对策分别是：显式记录失败/拒绝样本、特征计算严格 point-in-time、候选池由约束库在 T0 重建而非从结果反推。

> 这项验证应在 MVP 编码之前用历史数据先跑一遍：如果离线回放都看不到相对基线的改善，先改策略与特征，不要急着搭平台。它能把最大的项目风险（R2 / R3）在花实验预算之前暴露出来。

### 17.3 golden set、影子流量与适用条件

- **golden set**：冻结一组代表性配方，覆盖各材料体系、性能区间、边界与失败案例；任何特征/模型/规则变更都必须在其上回归。集合本身版本化，变更需审批。**自动化测试只用合成或脱敏数据，绝不拿真实配方做测试 fixture**——这是数据红线的延伸。
- **影子流量**：新模型与生产模型并行推理但只记录不返回，用于上线前对拍；小样本场景下比在线 A/B 更合适。
- **冠军挑战者**：用于评估门禁通过后的候选版本，观察期按「实验回写周期」而非固定天数设定。
- **在线 A/B**：仅用于 UI/交互层；模型效果判定因样本量太小、实验周期太长，统计功效不足，不作为主要依据。

### 17.4 故障注入清单（上线前必跑）

| 注入 | 预期行为 | 观测点 |
|---|---|---|
| 推理服务延迟 / 5xx | 切热备或 503，不返回模拟数值 | 错误码、降级级别 |
| 特征缓存全失效 | 走重算且 P95 仍在预算内 | 分环节耗时 |
| 事件重复投递 / 乱序 | 幂等消费，投影状态不重复、不错序 | 对账报告 |
| QC 大面积阻断 | 快照不推进，死信与人工队列可见 | 积压看板 |
| LIMS 长时间不可用 | 本地落库 + 重试 + 对账补齐 | 同步延迟 |
| 快照内容校验失败 | 冻结失败并回滚，训练不启动 | snapshot 状态 |
| GPU Job 被抢占 | 可续训，无半成品发布 | registry 状态 |
| 节点时钟漂移 | 事件时间与快照时间一致，告警 | 时间偏差指标 |

### 17.5 上线 go / no-go 检查单

- [ ] 三元组（模型 / 特征 / 快照）绑定校验通过，可复现重训差异 <1%
- [ ] §5.5 评估门禁全项通过，覆盖率与违规率达标
- [ ] golden set 回归无劣化，金丝雀配方集通过
- [ ] 离线回放证明策略相对基线有改善（§17.2）
- [ ] 契约测试、幂等测试、故障注入清单全部执行
- [ ] 降级四级链路演练通过，L4 能真正停止决策输出
- [ ] 审计完整率 100%，溯源可反查到原始配方
- [ ] 权限矩阵用例全覆盖，跨密级访问零命中
- [ ] 回滚包（应用 / 模型 / 迁移）齐备且恢复演练通过
- [ ] 气隙环境离线安装与升级演练通过
- [ ] 客户侧基线口径与验收指标已双方书面确认（§12）

## 18. 开发视图、演进治理与交付保障

### 18.1 代码结构与依赖方向（开发视图）

```
apps/
  web/             Vue3 前端
  api/             FastAPI 应用服务（无状态）
  workers/         Celery 任务（feature / batch / train / export）
packages/
  domain/          领域实体、化工规则、单位量纲（纯 Python，无框架依赖）
  features/        特征工厂：训练与推理的唯一实现
  models/          训练、推理、校准、解释、OOD
  contracts/       OpenAPI / JSON Schema / 事件信封定义
infra/
  helm/  k3s/  migrations/  offline-bundle/
docs/
  ARCHITECTURE.md  architecture/ITERATION_BACKLOG.md
tests/
  unit/  contract/  replay/  chaos/
```

**依赖规则（单向，CI 静态检查守护）**：`apps → packages → domain`；`domain` 不得依赖任何基础设施或框架；`features` 只允许被引用、禁止在 `apps` 内复制实现；跨服务只能经 `contracts` 定义的接口通信，**禁止直连对方数据库**；`models` 不得反向依赖 `apps`。用 import-linter 之类的工具把规则固化，违反即构建失败。

### 18.2 Walking skeleton（一期第一增量）

最薄端到端链路，目标是先把三条主线各打通一次，暴露集成问题而非算法问题：

1. 一份脱敏配方 CSV → 导入 + 阻断级 QC
2. 版本化快照 + 单位归一
3. 特征工厂产出固定 `feature_set_version`
4. 训练 2 个高价值指标的 LightGBM + conformal 校准
5. 工作台单点预测：数值 + 区间 + 溯源 + OOD 标记
6. 约束过滤下的 1 个批次候选推荐
7. 人工录入 1 条实验结果 → QC → 新快照
8. 触发重训，门禁通过 → 新模型版本
9. 下一轮推荐结果与上一轮不同（闭环可见）
10. 全过程审计可反查

**明确不含**：多租户管理 UI、LIMS 对接、知识图谱、生成模型、GNN、私有 LLM。这与 ADR-12 一致——一期的瓶颈是数据治理与闭环，不是功能广度。

### 18.3 多租户隔离级别选型（补 §8.2 的落地）

| 方案 | 隔离强度 | 运维成本 | 适用 |
|---|---|---|---|
| 共享库共享 schema + RLS | 中高（依赖策略正确性） | 低 | **推荐默认**，按项目组/项目隔离 |
| schema-per-tenant | 高 | 中，迁移需逐 schema 执行 | 子公司级隔离 |
| db-per-tenant | 最高 | 高 | 高密级客户、气隙独立交付 |

默认方案落地要点：所有业务表带 `tenant_id / project_id`，启用 PostgreSQL **Row-Level Security**，策略由会话变量（`SET LOCAL app.tenant_id`）驱动，而非依赖应用层手写 `WHERE`；连接池每次借出必须重置会话变量，防止串租户。

> **容易被漏掉的一处**：离线训练与批量导出同样必须走 RLS 上下文。只在在线链路上做 ABAC、训练脚本用高权限账号直读全库，会让 §8.2「禁止跨密级训练」在离线链路被完全绕过。训练任务应使用专用低权限角色，并把可见数据范围写入快照元数据以便审计。

### 18.4 Schema 演进、气隙升级与三层回滚

- 迁移工具：Flyway / Alembic；**只增不删**的扩展-收缩模式：加可空列 → 双写 → 回填 → 切读 → 下个版本才删旧列，保证任意版本可回退。
- 升级前校验兼容矩阵：`model_version × feature_set_version × schema_version`，任一不匹配则拒绝升级。
- 气隙升级包内容：容器镜像、迁移脚本、模型产物、依赖 wheel 包、校验和清单、回滚包、演练脚本、变更说明。升级前强制做一次快照备份与恢复演练，校验和不通过直接拒绝升级（F10）。
- **回滚分三层且彼此独立**：应用版本（镜像回退）、模型版本（指针切回 + 双缓冲旧版保留）、数据迁移（扩展-收缩保证旧代码可读新 schema）。只做应用回滚而忽略模型与数据，是私有化升级事故的典型成因。

### 18.5 架构守护（fitness functions）

把架构约束变成 CI 中可自动检查的不变量，防止随迭代腐化：

| # | 不变量 | 检查方式 |
|---|---|---|
| 1 | 无跨服务直连数据库 | 依赖扫描 + 连接串白名单 |
| 2 | 每个预测响应含 provenance 三元组 | 契约测试断言 |
| 3 | 特征版本与模型版本绑定 | 注册中心校验 |
| 4 | 无破坏性 API 变更 | OpenAPI diff |
| 5 | 真实数据 / 密钥 / 模型产物不入库 | CI 扫描 + `.gitignore` |
| 6 | golden set 回归通过 | 流水线门禁 |
| 7 | 每条推荐可追溯到 recommendation 记录 | 对账任务 |
| 8 | 训练任务使用低权限角色且带 RLS 上下文 | 权限审计 |

### 18.6 迭代节奏与责任边界

**每轮迭代的固定动作**：明确目标 → 记录变更的 ADR → 实现 → 产出验证证据（§17）→ 同步文档集 → 走 go/no-go 检查单 → 复盘并更新 backlog。缺少验证证据或文档同步的迭代不算完成。具体节奏与排期见 `docs/architecture/ITERATION_BACKLOG.md`。

| 决策事项 | 负责（R） | 批准（A） | 咨询（C） | 知会（I） |
|---|---|---|---|---|
| 模型版本上线 / 回滚 | 算法负责人 | 研发主管 + 客户方技术代表 | QC、审计 | 全体工程师 |
| 实验推荐采纳与调整 | 配方工程师 | 研发主管 | 算法负责人 | 实验员 |
| QC 阻断规则变更 / 裁决 | QC 负责人 | 客户方质量代表 | 领域专家 | 数据团队 |
| 数据分级与权限变更 | 系统管理员 | 客户方信息安全负责人 | 合规 | 全体 |
| 配方导出 / 对外演示脱敏 | 申请人 | 双人审批 | 系统管理员 | 审计 |
| 气隙升级与回滚演练 | 交付团队 | 客户方运维负责人 | 研发主管 | 全体 |
| 验收指标与基线口径 | 项目经理 | 双方负责人 | 算法、业务 | 全体 |

> §16.2 的静默失败防护与 §17.2 的离线回放，是「方法论与交付保障」章节里最能体现可信度的两块：前者说明我们知道 AI 系统会怎么骗人，后者说明我们能在花客户实验预算之前先证明自己有效。

## 附录 B：待客户确认的开放问题

1. 目标材料体系与优先优化的 2–3 个性能指标及其测试标准、目标区间。
2. 历史数据的实际规模、格式、标签口径与可用样本量（决定 ADR-02 是否需调整）。
3. 现有 LIMS/ELN/ERP 厂商、版本与可提供的集成接口（决定二期对接方案）。
4. 部署环境：是否已具备 K8s、GPU 资源，是否要求完全气隙。
5. 数据分级标准与合规要求（含导出审批流程、日志保留年限）。
6. 「实验轮次下降」的统计基线与验收口径。
7. 多租户边界：按项目组、子公司还是客户隔离，是否存在跨项目共享模型的诉求。
8. 降级偏好：L2 / L4 状态下客户可接受的最小功能集是什么（决定 §16.3 分级阈值）。
9. **历史实验序列是否完整保留失败与取消记录**（决定 §17.2 离线回放是否可行；只有成功配方会造成幸存者偏差）。
10. 气隙环境的升级窗口、备份与恢复演练责任人（§18.4）。
11. 模型上线、数据导出、QC 裁决在客户组织中对应的具体岗位（§18.6 RACI 落地）。
